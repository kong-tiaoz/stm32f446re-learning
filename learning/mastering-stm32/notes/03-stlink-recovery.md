# 2026-10-30：ST-LINK 失联与恢复复盘

## 结论与边界

本轮故障发生在 **ST-LINK 到 F446 的调试连接阶段**：USB 能识别 ST-LINK、目标电压约 3.23 V，但读取内核 ID 失败，尚未进入新固件下载。官方升级工具将板载调试器从报告 V2J28M18 的状态升级为 V2J48M35，配合重新插拔 USB 后，用户的官方 GUI 下载成功，原 VS Code 任务脚本也完整通过。

因此，本轮有效恢复操作是 **官方 ST-LINK 固件升级和 USB 重新枚举**。旧固件状态、升级后的调试器重新初始化是优先原因线索；现有证据不足以拆分两者的作用，更不能认定探针曾自行降级、硬件损坏或用户改变接线。VS Code 任务配置和编译产物无需修改即可完成同一流程。

还要保留一个限制：第一次成功烧录后，立即读内存的尝试已失败，当时日志仍报告 V2J48M35。此次恢复不能反向证明所有历史失败都是 V2J28M18 引起。最初寄存器程序中的 WFI 可能影响运行中调试，但本轮没有对它做对照实验，不能将其当作已确认根因。

## 这次排查可以改进的地方

- 助手应更早对照首次成功日志中的 ST-LINK 版本，并用官方升级工具核实，而不是长时间重复修改连接参数。版本差异不能直接当根因，但应该优先验证。
- 应先把错误分层：USB 识别、目标连接、编译、备份、下载、校验、硬件现象。读 core ID 失败时，重新生成相同固件解决不了当前连接障碍。
- 首次寄存器测试包含 WFI，增加了调试状态这个排查变量。后续首烧基准宜优先采用简单持续运行的主循环；本轮未改写该历史测试工程。
- 固件改变后，脚本的“预期灯型”提示也应同步。已将末尾旧的 500/500 ms 提示修正为当前 100/900 ms，未更改烧录逻辑。
- 任何保护解除、全片擦除或接线变动都不应仅凭通用错误提示尝试。本轮恢复未执行这些操作。

## 下次在 VS Code 中重复

1. 在 CubeProgrammer 中先点“断开连接”，结束其他调试会话，避免工具同时占用 ST-LINK。
2. 保持现有 STM32 配置文件，打开型号工作区。
3. **终端 → 运行任务 → Flash (backup + verify)**，核对任务后缀是 **book-hello-nucleo**。
4. 观察构建通过、完整备份保存、`Download verified successfully` 和复位信息；任一步失败都不继续写入。
5. 观察绿色 LD2 是否亮 100 ms、灭 900 ms，分别测试黑色 RESET 与断电重启。这三项仍需用户实际观察，不能由 CLI 成功推断。

本轮助手通过命令执行工具复跑了 tasks.json 定义的同一 powershell.exe 参数与脚本，没有代替用户点击 VS Code 任务菜单；任务文件及 STM32 配置文件保持原样。硬件调试、断点和 CH5 工程尚未验收。

官方依据：[STSW-LINK007](https://www.st.com/en/development-tools/stsw-link007.html)用于通过 USB 更新 ST-LINK/V2-1 等调试器固件；[CubeProgrammer 连接模式说明](https://dev.st.com/stm32cube-docs/prog/2.23.0/en/docs/markup/CubeProg_UserManual/Main_window.html)解释 Under reset 与 Hardware reset。上述资料说明工具用途，具体恢复结论来自本机日志与用户实际结果。
